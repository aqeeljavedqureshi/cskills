# Specialist areas

Assign each row to a distinct specialist. Use the proposed output filename unless an existing matching document is suitable. Paths are relative to the project root. Supply only the specialist's assigned row alongside the specialist contract.

| Area | Proposed output | Sub-aspects to explore | When to consult and responsibility |
| --- | --- | --- | --- |
| Application purpose and scope | `docs/application-overview.md` | Problem and intended users. Core capabilities. Frontend, backend, and external system boundaries. | Consult when assessing feature scope to understand the app's purpose and responsibilities. |
| Domain and business rules | `docs/domain-and-rules.md` | Business vocabulary and UI/code naming differences. Entities and relationships. Statuses, transitions, and cross-screen business rules. | Consult when changing business behavior to follow domain meanings and lifecycle rules. |
| Users and access | `docs/users-and-access.md` | Identity, session, active account, and tenant. Roles and permissions. Route/action checks and backend enforcement. Expiry, denial, and tenant switching. | Consult when changing protected behavior to follow identity, permission, and tenant rules. |
| Features and user journeys | `docs/features-and-journeys.md` | Feature map and responsibilities. Main workflow entry points, steps, and completion. Effects across features. | Consult when changing a workflow to preserve user journeys and dependent feature behavior. |
| Routes and navigation | `docs/routes-and-navigation.md` | Route-to-screen mapping and definitions. Layouts, menus, tabs, nested routes. URL parameters, filters, refresh, direct links, redirects, and unknown routes. | Consult when adding screens or links to follow routing and navigation behavior. |
| Architecture and code map | `docs/architecture-and-code-map.md` | Startup and provider composition. Feature/shared/API/configuration folders. Placement and dependency boundaries. One representative feature spanning UI, API, and tests. | Consult before placing code to follow module boundaries and the reference feature structure. |
| Stack and engineering conventions | `docs/stack-and-conventions.md` | Tools and their jobs. Naming, TypeScript, component, and hook patterns. Coexisting approaches, preferred patterns for new work, and legacy handling. | Consult when implementing code to follow tool choices and established engineering conventions. |
| State and data flow | `docs/state-and-data-flow.md` | Local, form, URL, shared, and server state ownership. Fetching and cache reuse. Mutation refresh/invalidation. Persistence and navigation/logout/tenant reset. | Consult when changing state or mutations to preserve ownership, caching, and reset behavior. |
| APIs and integrations | `docs/apis-and-integrations.md` | Services and supported features. Contracts, types, and clients. Authentication/tenant request context, pagination, filters, and error handling. | Consult when connecting data to follow service contracts and request conventions. |
| UI and interaction standards | `docs/ui-and-interactions.md` | Reusable components, tokens, layouts, and examples. Forms, tables, dialogs, validation, confirmations. Loading/empty/success/error states. Keyboard, accessibility, responsive behavior, languages, RTL. | Consult when changing interfaces to follow design, interaction, accessibility, and localization standards. |
| Setup and runtime | `docs/setup-and-runtime.md` | Runtime, package manager, startup commands, and services. Required configuration names and safe examples. Environment differences, API targets, feature flags, base paths. | Consult when running or configuring the app to follow setup and environment requirements. |
| Verification and change rules | `docs/verification-and-change-rules.md` | Lint/type/test/build commands. Test layers and examples. User-visible completion and required checks. Generated files, documentation synchronization, and decisions requiring human input under existing project rules. | Consult when verifying changes to apply validation commands and completion requirements. |

Keep full route lists, permission matrices, schemas, and detailed command variations in their existing source locations. Link only where needed for action. Explore all assigned sub-aspects even when the final concise document can summarize them together.
